## 各任务共同遵循的验收约束

- 使用项目业务术语和已确认决策：所有购买身份可微信购买普通商品，代理另可用积分；产品包公司转款不发积分；奖励由品牌方人工核算并线下结算。
- 用户只访问本人资料和业务记录；后台按功能授权；收款、积分、审核、价格、发货、退款、奖励和结算等关键操作可查询操作者、对象、时间、结果与原因。
- 历史业务保留当时身份、成交金额、归属和规则依据；后续配置只用于适用的新业务。金额与积分使用精确数值，来源及单位明确。
- 经营参数由品牌方提供并在对应任务中维护；缺失必要配置不得以原型示例或静默零值代替。商品价格归 03，配送与待成交依据归 04，订单有效期归 05，产品包与入驻依据归 07，收款说明归 02/07/08，奖励档位归 07/14，售后政策归 10，月结日期归 17。既有参数维护能力可复用，避免重复建设。
- 业务数据仅逻辑删除，正常查询过滤删除标记并保留历史引用。使用 MySQL 时统一采用项目规定的主键、创建修改用户 ID、毫秒创建修改时间和删除标记；唯一约束支持必要的重复写入，不通过物理删除处理冲突。
- 支付、积分发放、退款及必要补偿保留请求或追踪编号和业务键；仅对需要重试或人工补偿的事项持久化失败状态。批量操作逐项判定，失败不记成功。
- 验证用户可观察的金额、状态、余额和记录一致性；支付、退款、积分等资金路径验证必要的幂等与并发约束。普通展示和可逆低影响配置避免堆叠与实现重复的测试。
- 窄范围前端修改优先相关 lint、类型检查或测试；完整构建仅在用户要求或实际存在广泛构建风险时执行并提前说明。若使用 Java，运行 Java 工具前显式确认并使用 JDK 8，模型及字段提供完整中文 Javadoc，注释日志中文为主。
- 小程序主要路径检查微信顶部和底部安全区、文字可读性及真实身份展示；公开浏览不强制登录。
- 每项交付说明改动、验证结果和实际外部条件；真实微信支付退款、手机展示和人工转账须在具备条件后验收，不用本地替代结果声称真实交易已通过。

## 首期完成条件与外部准备

- 18 项均完成并逐项提供验收证据后，才能认为首期已具备完整业务能力；中间单项完成只代表对应路径可演示。
- 18 完成前，17 对有待收回奖励的对象保持待处理，不能跳过抵扣直接全额再付；首期最终交付须验证退款、冲回、月结、抵扣和追回连续路径。
- 品牌方上线前提供商品规格与价格、产品包及门槛、两档入驻奖励金额、真实公司收款资料、客服、售后期限政策、固定配送政策、月结日期、待付款有效期和微信商户资料。这些是上线输入，不增加范围外功能。
- 社区、问诊、课程、多层奖励、自动奖励生成或打款、在线提现、营销赠送、混合支付、在线积分充值、银行自动对账、实时物流轨迹及通用规则引擎均不在本批任务内。
