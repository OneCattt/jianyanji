# 寄存现有流程梳理（2026-10-28）

本记录保留2026-10-28修复前的流程诊断，后续修复结果以[修复交付记录](storage-flow-fix-20261028.md)为准。原梳理依据 CONTEXT.md、ADR 0007、customer-storage-points 规格和源码静态核对；本次未操作生产数据。

版本边界：项目交付记录记载后端/管理端已部署寄存能力，小程序未上传发布；本次工作区的小程序寄存、提货、套餐页面及其他界面仍有未提交改动。本记录中的小程序行为以当前本地代码为准，不能直接等同线上微信版本。

## 一、三类主要业务记录

| 记录 | 负责什么 | 关联关系 |
| --- | --- | --- |
| 购买订单及订单明细 | 成交商品、赠品、价格、支付来源、身份/归属、退款、累计发货与收货 | 一笔订单可分多次交付 |
| 寄存批次 | 用户已付款但留在品牌仓的货品数量、占用、原成交价、有效期 | 按原订单明细建立；相同SKU跨订单仍是不同批次 |
| 提货单及提货明细 | 本次配送的货品、地址、运费、审核、物流和确认收货 | 可跨多个原订单，也可同时包含本次新购首发商品 |

此外有实际发货记录。跨订单提货只有一个实体包裹、一套物流，但会按来源订单分别生成关联发货记录。

特别注意：当前普通新购的立即配送部分也会生成提货单，并非只有“从云仓取货”才使用提货单。

## 二、购买并建立寄存

1. 总部核实线下充值到账，为客户发积分；充值本身不授予身份。
2. 后台按SKU开放寄存。秒杀、小样、临期分类不能开放；普通商品、权益包和活动套餐均受商品是否可寄存限制。
3. 客户选择本次购买数量，以及每行“本次发货数量”；两者之差为寄存数量。默认本次全部发货。固定权益包、活动套餐另有全部寄存选择及逐行发货数量。
4. 客户可以同时选已有寄存货品，合并到本次配送；有旧寄存时，至少要有一行新购商品本次发货，不能“新购全部寄存＋只发旧寄存”。
5. 服务端报价并冻结商品、身份、地址、发货/寄存数量及运费。即使全部寄存，当前也必须提供有效且支持配送的地址。
6. 提交订单先预占本次购买的可售库存；如合并旧寄存，同时占用旧寄存数量。此时尚未扣积分、尚未建立新寄存所有权；需要配送的部分建立“待积分支付”提货单。
7. 客户再确认积分支付：扣积分、扣可售库存并释放销售预占，按订单明细建立寄存批次；权益包支付成功同时激活身份。相关步骤在同一业务事务内处理。
8. 支付后，纯新购首发提货单自动进入“待发货”；包含旧寄存的提货单进入“待审核”。全部新购均寄存且未带旧货时，不生成提货单。

例如购买10件，本次发2件：支付时扣10件可售库存，建立8件寄存，另外2件进入本次配送；后续提取寄存不再扣可售库存或商品货款。

## 三、单独申请寄存提货

1. 客户进入“我的寄存”，按原购买批次查看余量、提货占用、退款占用和到期日。
2. 输入本次提取数量，可跨页、跨原订单选多个批次。
3. 当前使用已选收货地址或默认地址报价；没有地址时跳转选地址。独立提货没有专门的地址与货品确认页面，以弹窗确认件数、运费及积分余额。
4. 提交时服务端再次检查本人归属、原订单有效付款、有效期、可提数量、配送范围和运费。
5. 在同一事务中生成待审核提货单、占用寄存数量、立即扣本次运费积分；余额不足则回滚，不保留部分成功结果。
6. 总部审核：通过进入待发货；驳回则释放占用、退运费，并生成驳回消息。
7. 总部填写物流发货：整张提货单一次出库，减少寄存剩余及提货占用，增加原订单已发货数量。当前提货发货接口不支持同一提货单再分多个包裹、分次发货。
8. 客户确认收到整个包裹，累计各原订单收货数量。跨订单包裹也一起确认，不能在本次提货单中只确认部分商品。
9. 原订单仍有未交付寄存时不会完成；签收部分可进入奖励可结算额度，实际奖励仍按人工月结规则办理。

提货状态顺序：待审核 → 待发货 → 已发货 → 已收货。待审核可以驳回；待审核及待发货可以取消。合并购买的提货单前面还有“待积分支付”，需要通过原购买订单付款或取消。

## 四、数量与运费口径

寄存当前可提数量 = 剩余寄存 − 提货申请占用 − 退款占用。

以8件寄存为例：申请提3件后，剩余仍为8件、提货占用3件、可提5件；实际发货后，剩余变为5件、该申请占用释放；取消则恢复8件可提。

| 本次配送组成/客户身份 | 当前运费 |
| --- | --- |
| 只有新购配送，无旧寄存 | 免费 |
| 新购商品金额满1000元，同时带旧寄存 | 免费 |
| 其余含旧寄存，普通顾客/2980店主 | 免费 |
| 其余含旧寄存，19800店主 | 本次提取旧寄存按原成交金额满1000元免费，否则10积分 |

赠品金额为0，不凑包邮门槛。旧寄存金额按原批次单价乘本次提取数量计算；身份取本次申请或购买报价时的有效身份并保存。

当前用于合并配送包邮的新购金额，是整笔新购商品金额，包含其中本次留仓的部分；是否应只计算本次实际配送的新货金额，需要业务明确，不能直接作为已确定的缺陷处理。

## 五、取消、退款、过期和历史订单

| 场景 | 当前处理 |
| --- | --- |
| 新购未付款取消/超时 | 释放新购销售预占和旧寄存提货占用，关闭关联未付款提货单；不退尚未扣除的运费 |
| 已付款提货取消/驳回 | 释放旧寄存提货占用、退本次运费；不退商品货款，不自动改变新购商品为寄存 |
| 寄存商品退款 | 从原购买订单走售后；申请先占用退款数量，成功才减寄存并按原积分来源退款，驳回释放占用 |
| 已有提货占用的货品申请退款 | 对无法取得可退款寄存数量的申请拦截，提示先取消提货；不是提交售后自动撤销提货 |
| 已发货后的运费退款 | 财务独立审核办理，与商品货款退款分开记账 |
| 商品/权益包退款 | 不自动关闭店主身份；身份关闭另外办理 |
| 寄存到期 | 上海付款日期加12个日历月，到期当天有效；过期禁止客户自行提货，但不清零、不收回所有权 |
| 过期办理 | 后台人工提货或延期，记录原因；人工提货仍核对数量、运费并进入审核 |
| 老订单转寄存 | 后台按订单明细人工转换，须有效已付款、白名单、真实未发数量且无冲突占用；不重复扣款、扣库存；有效期仍依据原付款日 |

到期提醒默认提前30天、7天生成站内消息；微信订阅消息另依赖模板配置、用户授权和发送结果，不能用站内消息已生成代替微信已送达。现有代码主要有到期和驳回提醒，没有完整的审核通过、发货、签收通知链。

## 六、目前已看出的流程衔接问题

下列为源码可见的行为或缺口；未进行真机及生产场景复现。

1. **购买订单状态无法表达寄存。** 全部寄存支付后仍显示“待发货/品牌仓正在配货”；部分发货签收后只要还有寄存，原订单仍可能显示“运输中”。客户难以区分“正常留仓”和“仓库尚未发货”。
2. **普通配送与寄存提货共用提货单，后台入口不直观。** 普通新购首发也被提货单占用，不能直接从旧订单发货入口再次发货，需要到提货模块办理。
3. **取消合并配送后，新购货品没有回到寄存。** 旧寄存恢复可提，新购未发货部分则重新成为普通订单可发货数量，需要总部到订单模块继续发货，或者另行转寄存。客户端取消提示没有解释这部分的去向；对纯新购首发提货单也会展示“恢复寄存”的通用说明。
4. **购买选择返回后会丢失或重置。** 活动套餐每次 onShow 都将逐行发货数量重设为全部发货；权益包重新加载时 choose() 也会重设数量。选择地址、合并寄存后返回可能触发，且“全部寄存”模式与逐行数量存在不一致风险。寄存选择页每次新进入也不回填之前的合并选择，修改选择不连贯。
5. **普通商品改发货数量后，报价失败仍保留旧报价。** 修改数量先更新本地选择，再请求报价；失败只显示错误，没有清空原报价。后续提交仍按旧 quoteId 建单，用户修改的意图与最终订单可能不同。服务端按原报价执行，但界面需要阻止用户误用旧报价。
6. **寄存卡片数量口径混杂。** “购买总量、累计已提”来自整条原订单明细，包含首发配送；“剩余寄存”来自寄存批次。例如买10、首发2、寄存8，首发后会显示累计已提2、剩余寄存8，容易被理解为从寄存又提了2件。
7. **提货确认和运营调整能力有限。** 独立提货只在弹窗确认件数和费用；提交后没有修改地址、数量的入口，只能取消重建；一张提货单必须整单发货、整包确认收货。

其中状态表达、取消后货品去向、发货入口和返回时保留选择，是后续整理产品流程时应优先明确的部分。
