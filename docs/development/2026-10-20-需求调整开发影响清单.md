## 最新调整：V2.1 首期线下交易

2026-10-20 用户确认：“首期不做支付相关，支付均线下交易”。下方第 1～7 节保留为此前 V2.0 的静态评估快照，其中微信付款、产品包双渠道、微信原路退款、支付商户资料及渠道验收要求已取消。当前范围以 V2.1 及 [任务 36](../../.scratch/jianyanji-phase1/issues/36-offline-transactions.md)为准。

| 链路 | 当前实施要求 |
| --- | --- |
| 普通商品 | 下单→线下付款→财务核款→可发货及核算收益；新增真实普通订单收款关联，普通货款不发积分 |
| 产品包 | 付款前确认资格及关系，财务核实线下到账后激活及建立交付，不额外发积分 |
| 积分 | 继续公司转款充值、核款发积分和原有积分订货，价格和原批次退款规则保留 |
| 现金退款 | 财务线下办理、登记真实结果及凭证，成功后联动资格和原收益人冲回；不调用渠道退款 |
| 已有线上支付 | 收口小程序与后台入口、服务端发起接口和支付渠道定时查询；保留历史数据，有真实存量未决交易时先核实处理 |
| 交付与验收 | 不要求支付商户、证书、支付通知／查单／关单／退款联调；保留微信登录、分享、视频及真实线下收退款核验 |

任务 24 改为 `wontfix`，25、33 改依赖 23、36 等对应任务，35 按 V2.1 重新记录本地验收。当前已完成应用改造及专用隔离库 V11 迁移验证，结果与上线要求见 [线下交易实施说明](v2-offline-transactions.md)；未运行实际资金渠道或迁移默认业务库。

## 调整前评估快照

日期：2026-10-20。依据用户最终确认的[首期需求规格说明 V2](../requirements/清欣简妍肌首期需求规格说明V2.md)及四轮 Q1～Q27，对 Java、MySQL、原生小程序和 Vue 后台作静态分析。代码现状为整理时的快照，实施前须复核工作区并行改动。

## 2 必须联动的代码路径

### 2.1 价格到实际成交

`CatalogService.rolePrice` → `OrderService` 购物车／报价／创建订单 → 小程序商品及结算页 → `PaymentService` 或钱包支付 → `RewardService` 原价格依据。

不能只在商品页显示 7 折或 3.5 折，订单仍读取旧手填档价。普通和福利品混合下单时，价格及收益资格按商品分别判断。所有价格、数量、类型和收益依据保留历史快照，改当前配置不改旧订单。

### 2.2 产品包付款到资格生效

`MembershipService` 资格／关系确认和产品包订单 → `PaymentService` 微信结果或财务核实公司收款 → 有效收款与交付订单 → 资格激活 → 后续身份定价。

当前 `receipt` 同时登记收款、扣实物库存并建立已付订单，不能直接再叠加一个微信已付订单。需统一产品包有效订单和激活入口，复用既有幂等、未决结果及库存机制；外部渠道调用不放进长数据库事务。

### 2.3 实际退款到资格和奖励

`AftersalesService` 实际退款成功 → 原积分批次返还或原渠道退款记录 → `MembershipService` 本次资格撤销／恢复 → 团队交接依据 → `RewardService` 各收益人冲回和欠款。

当前产品包资格处理硬性限制 offline，且假定存在原公司收款，必须适配微信产品包。不能让渠道已经退款而资格长期停留在激活状态；需要补偿时可按原退款编号重查并恢复一致性。已付奖励保持原收益人的欠款归属，不随团队交接转给新主理人。

## 3 数据库迁移影响

| 现状 | 迁移要求 |
| --- | --- |
| SKU 具有三档价，尚无明确普通／福利品业务分类 | 补充商品类型和相应有效价格依据；既有 SKU 分类及新零售价须核验，不将历史成交价格重算为新折扣 |
| 用户主要关联一笔当前入驻 | 保留多次资格及各自真实来源、有效性和前后关系，使恢复原店主有依据；首批存量资格与真实新购包分开记录 |
| 产品包依赖线下公司收款 | 扩展产品包订单与微信交易的关联，同时保留公司转款来源；同一申请有效付款及激活防重 |
| 普通订单缺销售代理和佣金历史依据 | 增加可追溯销售归属及原比例／商品范围，订单无代理与未知归属不能混为一类 |
| `rewards.kind` 的 CHECK 仅允许 onboarding、margin，唯一约束是有效订单加 kind | 扩展允许的奖励类型和收益人维度，确保一笔合法多收益人奖励可登记，同时禁止同来源同奖励重复登记；同步修改登记、结算和冲回逻辑 |
| 没有内容审核发布及团队交接业务记录 | 补充必要业务数据和审计，不为普通内容 CRUD 另造失败持久化平台 |

新增后续编号的 Flyway 迁移，不修改已应用的历史迁移，不物理删除业务数据。新增表按项目约定使用主键、创建修改用户、毫秒创建修改时间和逻辑删除字段；活跃唯一约束须兼容逻辑删除后重新办理。

存量记录只能沿实际证据迁移。旧订单没有销售代理，不补造零售佣金；首批资格登记不补造产品包收款；无法从真实资料确定的商品分类、原资格或关系，由品牌方核验后补齐，不能在请求中增加多轮数据库探测和自动猜测。

| 端 | 需要调整或新增的位置 |

| 售后和奖励 | `pages/refunds` 增加本人申请；`pages/rewards` 区分收益来源、收益人和冲回结果 |
| 品牌后台 | 现有 `BusinessSettings.vue`、`MembershipOperations.vue`、`PaymentOperations.vue`、`AfterSalesOperations.vue`、`RewardOperations.vue` 等按新流程修改；新增内容及资格／归属管理页面或业务区 |
| 用户接口 | 新增受本人授权的售后提交、团队限定查询、销售归属确认及内容公开查询；旧接口兼容范围在开发规格中逐项列明 |
| 后台接口 | 新增首批资格核验、团队交接、内容审核发布及导出；保留服务端财务和隐私权限校验 |

分享参数在登录和页面跳转后仍应保留，但仅作为候选，不能绕过服务端资格校验。未发布内容不得被公开详情接口或直接链接读取。内容分享可关联商品，代理销售归属仍以每单确认及快照为准。

视频需实际可播放的媒体资源、域名和访问配置。现有部署文档主要覆盖商品图片 HTTPS 地址，不能视为已完成短视频管理和播放验收；本轮不引入视频剪辑、直播或完整课程媒体系统。

## 5 建议实施顺序

| 阶段 | 工作及完成条件 |
| --- | --- |
| 1 | 冻结总确认稿及数据口径，补齐商品分类、资格来源、奖励来源和幂等迁移方案；明确存量数据不补造收益 |
| 2 | 实施商品价格、邀请确认、产品包双渠道、资格激活／恢复及首批核验，跑通真实数据库业务链路 |
| 3 | 实施销售归属、零售佣金、多收益人奖励、退款冲回和团队交接，验证资金归属及历史依据 |
| 4 | 接入小程序售后申请、团队、课程入口、种草空间及后台内容／导出；可独立开展的内容页面不依赖奖励引擎 |
| 5 | 完成接口及数据库回归、权限和导出检查，再进行真实微信、真机、视频及品牌方财务履约演练 |

各阶段可拆分开发任务，但涉及同一付款、资格或退款结果的改动须作为完整链路验收，不能只按页面完成度判断上线。

## 6 必须补充的验证

- 普通商品和福利品混合报价、同身份双支付、分币取整以及改价不影响原单。
- 产品包微信与公司核款分别激活、重复结果和未决结果、付款失败保留原有效身份、不重复占库或发积分。
- 升级包全退恢复仍有效店主，原资格已撤销不恢复；首批资格按真实依据登记且不补发资金或奖励。
- 店主包两名收益人分别登记和退款冲回，主理人直接邀请不叠加500元；未知8,000元奖励关闭时仍可正常入驻主理人。
- 零售订单按单确认销售代理、无代理正常零售、代理自购不另计本人佣金、福利品无佣金、零售单不叠加订货收益。
- 多次部分退款和全退金额守恒，已结算收益形成原收益人欠款，抵扣／实收去重；失败回滚及原结果重查后可补偿。
- 本人售后申请和数量上限，团队查询及导出不越权，直接邀请主理人仅名单与状态，交接不转移历史收益。
- 品牌图文视频的审核、发布、下架、直接详情访问控制、关联商品及实际分享；四栏导航和真机安全区。

后端测试和其他 Java 工具显式使用 JDK 8，真实 MySQL 回归使用隔离库。旧 TypeScript 测试结果及上一版 Java 验收记录不代表上述变更已通过。

前端先做对应 lint、类型检查及必要路径验证；仅在用户明确要求或实际存在广泛构建风险时进行完整构建，并提前说明原因。微信商户支付、退款及真实银行到账须具备外部条件单独验收。

## 7 本轮核对结果与后续状态

本轮只整理需求、术语、决策及影响清单，静态核对了相关 Java 服务、控制器、MySQL 约束和原生页面。文档差异及内部链接另作检查，没有运行代码测试、编译、完整构建、数据库迁移或外部交易。

V2 已于 2026-10-20 获用户最后总确认，本地规格入口登记为 `ready-for-agent`。尚未新增本轮实施任务，实际开发及验收结果按后续任务记录；排期以实际任务范围及现有工作安排为准。
