三项由 Flyway 按版本顺序执行，已经成功应用的迁移不重复执行、不改文件。MySQL DDL存在隐式提交，不能假定V12失败时会把此前全部建表/改表回滚。失败后保留错误、检查实际结构与 Flyway 状态，先恢复一致性再继续；禁止盲目 repair 或重跑 V14覆盖运营已录入价格。

上线前先只读核对并把结果存到受控备份位置，避免将客户数据提交Git：

```sql
SELECT VERSION();
SELECT installed_rank, version, description, success
FROM flyway_schema_history ORDER BY installed_rank;

-- 迁移前保留原值及V14预期初值，运营逐项核对。
SELECT id, retail_cents, store_cents, principal_cents,
       CASE WHEN retail_cents>0 THEN NULLIF(FLOOR((retail_cents*70+50)/100),0) ELSE NULL END AS next_store_cents,
       CASE WHEN retail_cents>0 THEN NULLIF(FLOOR((retail_cents*35+50)/100),0) ELSE NULL END AS next_principal_cents
FROM skus WHERE product_type='regular' AND is_deleted=0 ORDER BY id;
```

## 订阅消息配置与诊断

后台提醒默认提前30、7天生成站内消息；需配置到期/驳回模板ID及字段映射（微信字段名映射title/body/expiresOn），真实AppID/Secret和用户主动订阅后，才具备尝试发送的条件。微信实际接收仍须真机核对，不能用站内消息存在代替送达。

每分钟处理最多30条待发送消息。后台可查询 delivery_state、last_error、attempts、request_id；失败/不可用/结果未知经核实后人工重试。sending超过5分钟转unknown，先核实送达，避免反复点击导致重复通知。当前 enabled 控制到期扫描，不是所有待发送消息的总开关；默认模板为空时保留站内记录，不能假定已发送微信。

故障核对先用接口requestId及订单/提货/消息编号串联日志与业务账。余额、寄存数量、奖励来源、退款来源分别对账；失败不得计成功，不通过直接改余额或删记录“修复”。

## 回退与数据恢复

应用回退与数据库恢复分开处理：回退JAR/dist不会撤销V12～V14，也不会恢复V14改写的价格。旧代码使用固定折扣和旧履约/奖励规则，不能假设新增表列兼容就能安全回退。

若新版尚未接受业务写入，保持停写，优先恢复经核验的迁移前数据库备份，再恢复对应旧应用和客户端入口；或者经专项验证确认旧应用能够读取现有结构及价格后办理受控回退。任何价格恢复均以原备份为准，不手工反推。

若新版已有充值、扣积分、提货、退款或身份动作，禁止直接整库回灌迁移前备份，否则会丢失真实业务。先停写、保存当前库与日志，逐笔对账及制定数据恢复/前向修复方案，再决定恢复范围。已真实发生的收款、退款、发货须保留凭证与补偿记录；本次没有提供自动降级SQL，也没有完成生产恢复演练。
