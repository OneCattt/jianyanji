# 寄存提货后的订单列表数量修复（2026-10-28）

## 问题与修复

用户反馈：寄存申请仅提1件，待发货却显示原订单全部商品。可复现原因是待发货仅按实际配送筛选了订单，卡片仍将 `snapshot.lines` 的原购买数量直接作为当前配送数量；接口的提货关联也只返回编号和状态，没有申请行数量。

- 后端沿用已有订单行、提货关联、包裹三次读取，不新增逐单查询；提货关联携带本来源订单的明细行及申请件数，跨订单合并不会混入其他来源商品。
- 按订单明细输出 `pending_ship_qty`（当前待发件数）及 `in_transit_qty`（未签收包裹件数），订单汇总为 `pendingShipQuantity`、`inTransitQuantity`。件数均为SKU单位；待发件数包含有效待审核/待发申请及未分配的普通新货，不重复计入新购配送占用；取消/驳回申请不计，已发及已签收按实际包裹状态区分。
- 小程序待发货、运输中按上述字段显示商品及件数，原购买数量和原订单金额另行标明；全部订单、含寄存及原订单详情保留原成交快照，详情标题明确为原订单商品。
- 只调整读取与展示，不修改提货申请、库存、余额、成交价、奖励或实际出库逻辑，无迁移及配置变化。

## 验证

- 修复前实际页面回归失败：原买两种商品，只提其中1件，仍返回2行全部商品。
- 修复前真实隔离MySQL场景失败：原买3件、申请1件，接口缺少当前待发件数；修复后校验待发1件、出库1件、在途1件、签收后在途0件、余货2件寄存。
- JDK 8 定向回归：StorageMysqlTest 23项（真实本机隔离库、0跳过）、MiniListTest 11项、OrderServiceTest 9项通过；同时覆盖取消后恢复普通配送和合并提货的来源数量。
- 小程序行为与模板定向回归57项通过，包含同规格主品/赠品独立计数、全部订单仍保留原件数；微信源码及模板/样式编译检查通过。
- 本机库为 `java_rewards_test_storagefix_20261028`，不使用生产账户或实际仓储物流。日志保存在 `.scratch/storage-order-quantity/`。
