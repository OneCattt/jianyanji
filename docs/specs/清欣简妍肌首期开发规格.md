# 清欣简妍肌首期开发规格

## Problem Statement

清欣简妍肌需要同时服务游客、调肤店主和调肤主理人，并由品牌方统一管理收款、代理审核、商品供应与售后。当前仓库只有已评审的需求、术语和业务决策，尚无业务代码、可用系统或测试。

游客需要直接购买商品；代理既需要直接微信付款，也需要向公司转款、取得积分后订货。品牌方需要清楚区分产品包货款、订货转款、积分余额、商品支付、退款以及代理奖励，避免同一笔资金重复发积分、同一订单重复扣款，以及退款后奖励和身份未同步处理。

仅实现商品页面无法满足首期目标。品牌方还需要核实到账、开通身份、发货、按原交易退款，并人工核算和月度结算代理奖励；购买者需要查询各自订单、积分、售后及奖励，知道当前处理结果。

## Solution

建设微信小程序和品牌方管理后台。小程序底部使用“首页、商城、我的”，提供购物、代理申请、订单、积分钱包及本人奖励明细；后台提供商品价格、代理审核、公司收款、积分、履约、售后、奖励和必要配置。

首期提供以下闭环：

- **微信购物**：游客登录后、店主或主理人均可选择商品并微信付款，品牌方发货，购买者查询物流、确认收货；同一购买身份不因使用微信或积分而改变商品价格。
- **积分订货**：代理按统一说明向公司转款，工作人员核实到账并按 1 元对应 1 积分发放，再由代理确认积分付款；小程序不提供在线微信充值。
- **产品包入驻**：申请人向公司转款购买产品包，品牌方核实收款、交付对应商品、审核身份并确认邀请归属；产品包款不额外发积分。
- **售后退款**：客服受理、后台审核，支持未发货退款、符合政策的已发货退货及按商品数量部分退款；商品订单原路退钱或退积分。未使用积分对应款项允许人工申请退现金，并受原公司收款与可退余额双重限制。
- **代理奖励**：直接邀请人获得两档固定入驻奖励；归属主理人获得店主订货价差收益。品牌方人工核算，符合收货及售后条件后每月集中线下转账。代理可查询本人明细，退款对应冲回、抵扣或人工追回。

首期目标是把真实交易和账务处理完整、可追溯地跑通。具体奖励档位金额、商品价格、期限和账户资料由品牌方上线前填写。

## User Stories

以下按“作为某角色，我希望某项能力，以便获得业务结果”的格式描述。A 为品牌方，B 为调肤主理人，C 为调肤店主，D 为游客；代理指 B 与 C。

1. 作为游客，我希望未登录也能浏览品牌和商品，以便了解产品后再决定购买。
2. 作为游客，我希望在需要下单时登录并提供必要联系方式，以便完成购买及收货。
3. 作为游客，我希望登录后仍清楚显示非代理身份，以便理解当前价格和可申请的权益。
4. 作为购买者，我希望按分类查看商品，以便快速找到需要的护理产品。
5. 作为购买者，我希望看到商品图片、说明、规格、价格和库存情况，以便选择合适商品。
6. 作为代理，我希望看到自己身份对应的价格，以便准确了解订货成本。
7. 作为代理，我希望微信和积分购买使用相同身份价格，以便根据余额选择支付方式。
8. 作为购买者，我希望选择规格和购买数量，以便购买正确的商品组合。
9. 作为购买者，我希望立即购买单个商品，以便快速下单。
10. 作为购买者，我希望将多个商品放入购物袋并勾选、调整数量或移除，以便统一结算。
11. 作为购买者，我希望购物袋区分商品种类与总件数，以便核对数量和合计金额。
12. 作为购买者，我希望维护收货人、电话、地区、地址及默认地址，以便正确配送。
13. 作为购买者，我希望下单前看到配送范围、运费和发货说明，以便决定是否付款。
14. 作为购买者，我希望库存不足、商品下架或价格变化时得到明确提示，以便重新确认购买内容。
15. 作为游客，我希望直接使用微信支付商品订单，以便无需申请代理或转款充值就能购买。
16. 作为代理，我希望仍可直接微信付款，以便无需等待公司转款确认就能订货。
17. 作为代理，我希望选择积分支付并确认实际扣减及余额，以便使用公司已发放的积分订货。
18. 作为代理，我希望积分不足时能查看转款说明或改用微信整单付款，以便完成购买。
19. 作为购买者，我希望支付结果区分成功、失败及确认中，以便知道是否还需操作。
20. 作为购买者，我希望重复点击、网络重试或回到页面不会再次付款，以便避免重复扣款。
21. 作为购买者，我希望继续支付未付款订单或取消它，以便处理尚未完成的购买。
22. 作为购买者，我希望查看自己的订单列表与详情，以便了解商品、费用、支付及履约进度。
23. 作为购买者，我希望已有订单保留成交时的价格和收货地址，以便后续修改资料不会改变已成交内容。
24. 作为购买者，我希望查询物流公司和运单号并复制单号，以便了解配送情况。
25. 作为购买者，我希望收到商品后确认收货，以便完成订单履约。
26. 作为申请人，我希望查看店主和主理人的入驻权益、产品包及申请要求，以便选择适合的身份。
27. 作为申请人，我希望提交申请并查看结果或驳回原因，以便知道是否已经取得代理身份。
28. 作为申请人，我希望按公司转款说明购买产品包并查询收款和交付情况，以便了解入驻进度。
29. 作为品牌方，我希望产品包货款只对应商品交付，以便不把同一笔货款再次发成可消费积分。
30. 作为品牌方，我希望核实条件后审核通过或驳回申请，以便控制代理身份的有效性。
31. 作为品牌方，我希望分别确认直接邀请人和归属主理人，以便正确记录业务关系和奖励对象。
32. 作为品牌方，我希望无邀请人或由店主邀请的申请也能人工指定归属主理人，以便完成正常入驻审核。
33. 作为申请人，我希望只有审核通过后才启用代理价格和积分订货，以便身份与权益一致。
34. 作为代理，我希望查看有效公司收款资料、转款备注及客服联系方式，以便完成订货转款。
35. 作为品牌方收款人员，我希望登记实际到账金额、时间、收款流水、用途和对应代理，以便查清款项来源。
36. 作为品牌方收款人员，我希望核实订货转款后按 1∶1 发积分，以便让代理使用已到账款项订货。
37. 作为品牌方收款人员，我希望同一笔款项不能重复发积分或同时抵作产品包货款，以便防止重复增加权益。
38. 作为代理，我希望查看积分余额及发放、扣减、退回记录，以便核对订货资金。
39. 作为品牌方，我希望误记积分能够通过保留依据的纠正记录处理，以便修复错误并保持历史可追溯。
40. 作为购买者，我希望能联系客服办理售后，并在小程序查询处理状态，以便知道是否需要寄回或等待退款。
41. 作为客服人员，我希望按原订单登记商品、数量、原因、拟退款金额及退货情况，以便正确受理售后。
42. 作为购买者，我希望符合政策的已发货商品可以退货，以便获得必要的售后保障。
43. 作为购买者，我希望一单中只退部分商品或数量，以便保留其他商品的正常履约。
44. 作为品牌方，我希望登记实际收到退货和验货结果，以便有依据地决定退款及库存处理。
45. 作为购买者，我希望微信支付退回微信、积分支付退回积分，以便核对原交易。
46. 作为品牌方，我希望退款数量和金额不能超过原订单剩余可退范围，以便避免重复退款或超退。
47. 作为购买者，我希望退款处理中或失败时看到真实状态，以便不误认为退款已经完成。
48. 作为代理，我希望可以人工申请退回未使用积分对应的公司转款，以便处理不再需要的订货余额。
49. 作为代理，我希望订单退款实际退回且尚未使用的积分也能申请现金退款，以便退回剩余预付款。
50. 作为品牌方，我希望积分余额退款核对原收款和剩余未退款金额，以便同一笔资金不重复退款。
51. 作为品牌方，我希望退款办理中的积分不能再次消费，以便现金退回后不会留下重复可用余额。
52. 作为代理，我希望积分退款失败或驳回后释放占用，以便继续使用仍属于我的余额。
53. 作为品牌方，我希望产品包全部退款后取消该次入驻身份，以便后续订单使用真实有效身份价格。
54. 作为品牌方，我希望产品包部分退货时审核是否仍满足身份条件，并保留历史订单和积分，以便准确处理权益变化。
55. 作为直接邀请人，我希望符合规则的入驻获得对应固定奖励，以便取得约定的邀请报酬。
56. 作为归属主理人，我希望店主订货按原成交价差产生收益，以便取得约定的订货收益。
57. 作为归属主理人，我希望店主使用微信或积分付款采用同一收益规则，以便支付方式不会改变报酬。
58. 作为品牌方核算人员，我希望保留订单当时的主理人价格、成交价及归属依据，以便人工核算时不受后续改价影响。
59. 作为品牌方核算人员，我希望只核算直接邀请入驻奖励和归属主理人订货收益，以便首期不引入多层分配。
60. 作为品牌方核算人员，我希望奖励区分未到结算期、可结算和已结算，以便不提前付款。
61. 作为品牌方核算人员，我希望收货完成、售后期结束且无待处理售后后才结算，以便控制退款带来的追回工作。
62. 作为品牌方付款人员，我希望每月集中向代理转账并登记收款人、金额和凭证，以便核对实际奖励支出。
63. 作为代理，我希望在“我的”查看本人奖励来源、金额、结算和冲回记录，以便了解实际收益。
64. 作为品牌方核算人员，我希望订货部分退款按原退货商品收益冲回，以便未退商品的收益得到保留。
65. 作为品牌方核算人员，我希望产品包部分退款按原货款退款比例冲回入驻奖励，以便奖励与实际入驻货款对应。
66. 作为品牌方核算人员，我希望全部退款冲回原奖励剩余全部金额，以便不因分次取整遗留差额。
67. 作为品牌方付款人员，我希望已付奖励优先抵扣同一人后续可结算奖励，以便减少额外追回款项。
68. 作为品牌方付款人员，我希望记录抵扣、人工追回和未收回金额，以便持续跟进差额且不重复扣回。
69. 作为品牌方，我希望管理商品、规格、身份价格、库存和上下架，以便开展日常销售。
70. 作为品牌方仓库人员，我希望只对符合条件的已支付订单发货并登记运单，以便避免未收款或待退款商品发出。
71. 作为品牌方仓库人员，我希望退货是否重新入可售库存以实际验货为依据，以便避免账面有货但实物不可销售。
72. 作为品牌方运营人员，我希望配置品牌内容、身份权益、客服和收款说明，以便保持购买者看到的信息有效。
73. 作为品牌方运营人员，我希望配置两档奖励、售后期、月结日期和配送政策，以便日常调整无需重新开发。
74. 作为品牌方，我希望配置修改只影响后续新业务，以便历史订单、积分和奖励不被改写。
75. 作为品牌方管理者，我希望按账号授权后台功能并查询关键操作记录，以便查清谁审核、发积分、发货、退款或结算。
76. 作为购买者或代理，我希望只能查询自己的地址、订单、积分和奖励，以便保护个人及业务信息。
77. 作为支持人员，我希望支付、发积分和退款的失败可按业务编号追踪，需补偿的事项可查询，以便处理真实异常。
78. 作为品牌方，我希望停用或移除业务资料保留历史记录，以便历史交易、审计和财务核对仍有依据。
79. 作为手机用户，我希望主要页面文字清楚、按钮不被微信界面遮挡，以便顺利完成购买和查询。

## Implementation Decisions

### 1. 当前基础与实现边界

- 已有业务术语及两项确认决策：公司收款发积分与微信付款并行；首期人工核算、结算奖励。实现须遵循这些约定。
- 当前没有应用代码、已有接口、数据库迁移或测试框架，因此本规格定义业务模块和可观察契约，不宣称复用不存在的实现。
- 技术栈、具体接口路径和表结构尚未选定，本规格不替开发选型，也不预设消息队列、微服务、规则引擎或异步任务平台。
- 若使用 Java，所有 Java 工具显式使用 JDK 8。代码注释、日志以中文为主，新增或修改的 Java 模型及字段提供中文 Javadoc，并明确状态、单位与可空性。

### 2. 身份与权限

- 品牌方 A 使用后台；B 和 C 为代理；D 是未取得代理身份的购买者，既包含未登录访客，也包含已登录非代理用户。
- 浏览不强制登录，购买和个人查询需要登录。新用户登录仍为 D，已有代理保留有效身份；后台权限与购买身份独立。
- 购买者仅访问本人记录。后台功能按工作人员授权执行，关键操作记录账号、业务对象、时间、结果和原因。
- 审核时分别确定直接邀请人与归属主理人，两者可不同；无邀请人或店主邀请时也由品牌方指定归属。首期不开放复杂自动绑定、递推及关系变更。

### 3. 页面及业务模块

- 小程序提供首页、商城、商品详情、购物袋、地址、结算支付、订单及物流、入驻结果、钱包、售后状态及本人奖励明细。
- 后台提供商品及规格、身份价格、代理审核、产品包收款交付、积分收款发放、订单履约、售后退款、奖励核算结算、配置与操作审计。
- 模块是业务职责划分，不要求分别部署，也不要求为每类业务另建通信或计算层。
- 首页移除首期未提供功能的入口；原型仅作视觉参考，示例价格、余额、日期、奖励不得直接作为经营参数。

### 4. 商品、价格和历史依据

- 按具体规格维护零售价、店主价、主理人价、库存和上下架。同一身份两种支付方式使用相同商品价格；一笔订单只使用一种支付方式。
- 主理人价不得高于采用该价差收益的店主价。结算前校验商品、规格、数量、价格、配送范围和费用；变化需要购买者重新确认。
- 商品订单保存成交商品、规格、数量、身份、价格、运费和地址。店主订单另保留当时主理人单价及归属依据。
- 历史订单、奖励和退款按原业务依据处理，后续改价、变更身份或调整奖励档位不重新计算历史来源。
- 购物袋区分种类和总件数；移除或修改常用地址不改变已有订单地址。

### 5. 公司收款、积分和产品包

- 订货积分转款经工作人员核实实际到账，按 1 元对应 1 积分发放，两种代理比例相同，无赠送积分或积分过期。
- 登记代理、金额、到账时间、收款账户标识、原收款流水、用途和必要凭证。一笔原收款首期对应一人，不能重复发积分。
- 发放结果与积分流水一致；纠正错误须留存来源、原因和操作记录，不直接无痕覆盖余额。
- 产品包首期只接受公司转款，关联申请、产品明细、实际收款和商品交付。产品包款不另发等额积分，不能同时作为积分发放来源。
- 产品包全部退款完成后撤销该次入驻取得的身份；部分退货人工审核是否仍满足条件。历史订单和积分保留，奖励冲回单独处理。

### 6. 订单、支付和履约契约

- 所有购买身份均可微信购买普通商品；B、C 额外支持积分。品牌方如使用购买端，同样遵循实际购买身份，后台权限不自带优惠。
- 创建订单不等于扣积分，用户最终确认积分付款时才扣减并记录支付；扣款、支付记录和订单结果须一致。
- 支付成功必须有真实核验依据。前端返回、关窗或网络超时不决定支付最终结果；未明结果展示确认中，支持查询和必要的人工处理。
- 同一订单只允许一笔有效支付；重复请求、通知、并发确认或支付取消竞争不得重复收款、扣积分、超卖或遗留永久库存占用。
- 结果未明时不能换支付方式重复付款，也不通过创建替代订单规避查询原结果。
- 订单支持待付款、待发货、已发货、已完成及已关闭；支付和售后各自保留处理状态。付款失败不自动等于关闭订单。
- 取消、超时、实际到账竞争均可追踪和处理。品牌方只对满足条件的已支付订单发货，待退款商品不得继续误发。
- 发货维护物流公司、运单号、操作人及时间，错填纠正留记录；购买者查看和复制单号，收货后确认完成。

### 7. 商品售后、积分退款契约

- 客服受理、后台登记及审核，支持未发货退款、符合政策的已发货退货和按商品数量部分退款；用户端查询状态。
- 售后关联原订单和商品，保留数量、金额、原因、退货及验货依据。已退和处理中的数量、金额占用可退额度，不能重复受理超量超额退款。
- 微信订单原渠道退款，以渠道真实结果为准；积分订单退回积分并关联原支付。退款失败、处理中和成功分别记录，不能把操作请求当成功结果。
- 退款不直接增加可售库存，须按实际收货验货结果决定返仓。未退商品继续正常履约。
- 未用积分对应转款可申请人工退现金，包括普通订单退款退回且未再次消费的积分；金额受可退积分与原公司收款剩余未退金额共同限制。
- 退款处理中的积分不得消费；实际退款成功后扣回，失败或驳回释放占用。保留原公司收款、积分退回和现金退款关联，防止同一资金被重复退回。

### 8. 奖励核算、结算与冲回

- 仅做直接邀请人的入驻奖励、归属主理人的店主订货收益，不做多层奖励。
- 入驻奖励按新加入者身份设邀请店主、邀请主理人两档固定金额，保存该次审核通过时适用的金额及依据。
- 店主订货收益为各商品“原实际成交单价减当时主理人订货单价，再乘实际数量”的合计；不含运费，微信与积分付款同规则，积分按 1∶1 对应货款。
- 首期由品牌方人工核算、登记并核对上述口径，不引入自动收益生成或自动打款。保留来源、对象、规则依据、金额和记录人。
- 对应商品收货完成、售后期结束且无待处理售后后，奖励可结算。入驻奖励还须具备已通过的申请、有效产品包收款与交付依据。
- 每月集中公司线下转账，记录结算月份、实际收款人、抵扣额、实付、付款时间和凭证。奖励不自动转成订货积分，也不开放在线提现。
- 店主订货退款按退货商品原单位收益及数量冲回；产品包按原入驻奖励乘累计退款货款比例核定累计应冲回，再扣除此前冲回金额。运费不计产品包退款比例。
- 全部退款冲回原奖励剩余全部金额。奖励结果精确到分，计算保留精度，登记两位小数四舍五入，累计冲回不得超过原奖励，全部退款补齐余数。
- 未付奖励冲回减少待付额；已付奖励优先抵扣同一人后续可结算奖励，不足人工追回。抵扣关联原待收回记录和本次应结算奖励，未实际收回不能标记完成。
- 小程序展示本人奖励来源、金额、结算、冲回及必要抵扣信息，不泄露无关人员订单或个人信息。

### 9. 数据、配置和诊断

- 持久化范围包含用户代理、审核归属、产品规格价格、产品包收款交付、订单支付履约、公司收款、积分余额流水、两类退款、奖励核算结算冲回抵扣、配置及操作记录。
- 金额及积分采用精确数值并明确单位，业务记录具有可追溯编号；不把订货积分流水视为现金支付流水。
- 业务数据仅逻辑删除，正常查询过滤已删除数据，历史交易与审计依据保留；唯一约束支持需要的重复写入，不能依赖物理删除解决冲突。
- 使用 MySQL 时采用既定的主键、创建修改用户 ID、毫秒创建修改时间和删除标记审计约定，不创建用户姓名审计字段。
- 配置包含身份价格、权益、入驻及收款说明、首页内容、客服、固定配送政策、两档入驻奖励、售后期和月结日期。修改校验并留记录，已成立业务保留当时依据。
- 配置数值缺失不能使用示例或静默以零代替。配置能力不意味着建设通用规则引擎。
- 支付、发积分、退款及必要的补偿操作记录请求或追踪编号、业务键、失败原因和实际结果。需要重试或人工补偿的失败事项可查询，不能重复成功记账；不为普通资料 CRUD 额外建设诊断持久化。
- 日志和用户查询仅暴露必要信息，避免完整敏感资料泄露。

## Testing Decisions

### 主要测试边界（拟议，待用户确认）

以应用对外提供的业务接口为主要测试边界：通过购买者和后台人员的业务操作建立数据、发起支付及售后，再查询订单、余额、奖励和操作结果。验证从调用者看见的业务行为，不以内部方法调用次数、私有结构或某条实现语句作为通过条件。

这是一个应用级业务测试边界；模块间使用真实业务实现和测试数据库。仅在应用外部替换微信支付、退款的测试适配，以及可控时间来源，以稳定覆盖回调、结果查询、售后期和月结日期，不为每个内部模块另造一套测试接口。

当前项目没有现有测试或接口可引用，也未选定运行框架，因此没有可复用测试先例。此处是实现前建议，不声称已得到用户确认、已实现或已通过测试。

### 覆盖范围和可观察结果

| 测试组 | 从业务接口验证的行为 |
| --- | --- |
| 身份与授权 | 登录不自动成为代理；审核后价格生效；购买者与后台权限独立；他人地址、订单、积分、奖励不可读写 |
| 商品与结算 | 规格数量、种类件数、运费、库存和配送校验正确；同身份双支付商品价一致；成交快照不被后续改价或改地址改变 |
| 收款与积分 | 核实一笔 1,000 元订货转款只发一次 1,000 积分；重复或并发提交不重复发放；产品包收款不能再发积分 |
| 支付与订单 | 微信或积分成功后订单进入待发货；重复点击和通知只记一次；余额不足不超扣；结果未明不重复付款；取消和到账竞争可核查 |
| 履约与库存 | 未付款不可发货；待退款数量受控；超时取消释放应释放占用；确认收货可查；退款不把未返仓商品直接变成可售库存 |
| 商品退款 | 原路退款、部分数量、并发受理、失败重查及成功通知重复均正确；不超退；未退商品保留履约关系 |
| 积分余额退款 | 审核占用 600 积分后，可用 1,000 只剩 400；实际退款扣回，失败释放；订单退回积分可申请现金但受原收款剩余额限制 |
| 入驻产品包 | 转款、审核、交付有依据；全退款撤销该次身份而保留历史数据；部分退货保留人工身份审核结果 |
| 奖励核算依据 | 两档入驻奖励匹配新加入者身份；订货收益引用原价差、数量和正确对象，排除运费；微信积分一致；不多层递推 |
| 结算和追回 | 未收货、售后期未结束或存在售后不可结算；月结登记实付与凭证；已付奖励冲回后抵扣和追回不重复、剩余差额可查 |
| 配置与审计 | 调整新价格和奖励档位不改历史依据；缺失必需配置不能默认为零；发积分、退款、身份、价格及结算操作可追踪 |

### 关键计算样例

以下全部为测试数据，不是实际经营配置。

1. 店主单价 100 元、原主理人价 80 元，数量 3、运费 10 元，订货收益为 60 元；退一件冲回 20 元。微信或积分结果一致。
2. 上述订单成立后，主理人价改为 70 元，原收益仍为 60 元，退一件仍冲回 20 元。
3. 产品包货款 1,000 元、原入驻奖励 200 元；先退货款 250 元冲回 50 元，再退 250 元再冲回 50 元；全退后累计冲回 200 元。
4. 分次退款产生不足一分的计算结果时，累计冲回不超过原奖励，全退补齐剩余，不能因逐次取整多扣或漏扣。
5. 已付奖励待收回 100 元，后续可结算奖励 80 元，抵扣后不再实转这 80 元，待收回剩 20 元；重复登记不再抵扣同一笔。

### 补充验证和外部边界

- 前端仅针对必要路径验证三类身份购买、转款说明、结果确认中、订单、钱包和奖励查询；检查文字可读、微信顶部区域和底部安全区，不为每个静态卡片新增测试。
- 前端窄范围变更优先相关 lint、类型检查或测试；完整构建仅按明确要求或实际广泛风险执行，并说明原因。
- 微信通知验签、真实支付退款、实际手机页面和公司人工操作须在具备条件后开展集成验收；本地替代外部支付的测试不能代替这些证据。
- 当前仅交付规格，没有执行业务测试、构建或支付验证。
